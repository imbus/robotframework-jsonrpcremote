```text
robot-jsonrpcremote-server [options] [LIBRARY ...]
```

The `LIBRARY` arguments are the libraries that clients may import. Without
them, clients may import any library that the server can import; see
[Several libraries on one server](/robotframework-jsonrpcremote/guides/several-libraries/).

## Options

| Option                         | Default                                              | Meaning |
| ------------------------------ | ---------------------------------------------------- | ------- |
| `--mode {tcp,stdio,pipe,pipe-server}` | `tcp`, or `ROBOT_JSONRPC_MODE`                | How clients connect: `tcp`, `stdio`, `pipe` or `pipe-server`; see [Transports](/robotframework-jsonrpcremote/guides/transports/). |
| `--tcp`                        |                                                      | Same as `--mode tcp`. |
| `--stdio`                      |                                                      | Same as `--mode stdio`: serve a single client over stdin and stdout. |
| `--pipe NAME`                  |                                                      | Same as `--mode pipe --pipe-name NAME`: connect to the pipe `NAME`, serve the client that listens there and stop when the connection ends; see [Pipe modes](#pipe-modes). A client that starts the server passes `--pipe=NAME` as the last argument. |
| `--pipe-server NAME`           |                                                      | Same as `--mode pipe-server --pipe-name NAME`: listen on the pipe `NAME` for any number of clients; see [Pipe modes](#pipe-modes). |
| `--bind ADDRESS`               | `127.0.0.1`, or `ROBOT_JSONRPC_BIND`                 | The address to listen on, in TCP mode. Repeat it to listen on several addresses. |
| `--port PORT`                  | `8271`, or `ROBOT_JSONRPC_PORT`                      | The port to listen on, in TCP mode. |
| `--pipe-name NAME`             | `robot_jsonrpcremote_pipe`, or `ROBOT_JSONRPC_PIPE_NAME` | The name of the pipe, in the pipe modes. |
| `--pythonpath PATH`, `-P PATH` | none                                                 | A directory to add to the Python path, as `robot --pythonpath` does. Repeatable. |
| `--variable name:value`        | none                                                 | A Robot Framework variable for the libraries, as `robot --variable` sets it. Repeatable. There is no `-v`, which is `--verbose`. |
| `--variablefile PATH`, `-V PATH` | none                                               | A variable file for the libraries, as `robot --variablefile` loads it. Repeatable. |
| `--outputdir DIR`, `-d DIR`    | the current directory                                | The value of `${OUTPUT_DIR}` for the libraries. The server writes no output files. |
| `-v`, `--verbose`              | off                                                  | Log debug messages, with timestamps. |
| `--send-tracebacks`            | off                                                  | Send the traceback of an unexpected error to the client; see [Errors and tracebacks](#errors-and-tracebacks). |
| `--pickles`, `--no-pickles`    | on, or `ROBOT_JSONRPC_PICKLES`                       | Whether the server reads and sends pickles, which carry Python objects that JSON cannot hold between Python peers; see [Values](/robotframework-jsonrpcremote/reference/protocol/#values). |
| `--version`                    |                                                      | Show the version and exit. |
| `-h`, `--help`                 |                                                      | Show the options and exit. |

## Environment variables

An option on the command line takes precedence over its environment variable.
A value that the option does not take, such as a port that is not a number,
an unknown mode or a value of `ROBOT_JSONRPC_PICKLES` that is no truth value,
ends the server with the usage error of the option and exit code 2, as on the
command line.

| Variable                  | Sets the default of |
| ------------------------- | ------------------- |
| `ROBOT_JSONRPC_MODE`      | `--mode`            |
| `ROBOT_JSONRPC_BIND`      | `--bind`; several addresses are separated by commas |
| `ROBOT_JSONRPC_PORT`      | `--port`            |
| `ROBOT_JSONRPC_PIPE_NAME` | `--pipe-name`       |
| `ROBOT_JSONRPC_PICKLES`   | `--pickles` and `--no-pickles`: `true`, `yes`, `on` or `1` turn pickles on, and `false`, `no`, `off`, `0`, `none` or an empty value turn them off, ignoring case, as Robot Framework reads them |

## Pipe modes

A pipe connects processes on one machine: a named pipe on Windows, a Unix
domain socket elsewhere.

- **Pipe mode,** `--pipe NAME`: the server connects to the pipe of a client
  that listens there, serves that one client and stops with exit code 0 when
  the connection ends. That is how the client starts the server for a
  `pipe:<command>` URI: it listens on a new pipe and appends `--pipe=NAME`.
- **Pipe-server mode,** `--pipe-server NAME`: the server listens on the pipe for
  any number of clients until it is stopped, as in TCP mode. Clients connect
  with `pipe://NAME`.

**Names:** on Windows, a bare name such as `robot` means the named pipe
`\\.\pipe\robot`, and a name that starts with `\\` or `//` is used as written.
Elsewhere, the name is the path of a socket file, relative to the working
directory of the server unless it is absolute. The platform allows 107 bytes
for that path on Linux and 103 on macOS.

**Who can connect:**

- On Windows, the pipe gets the default security descriptor: the user who
  started the server, administrators and SYSTEM can send requests. Other users
  can open the pipe for reading only.
- On Linux, a client needs write permission on the socket file, which gets its
  rights from the umask. A directory that only you can enter keeps other users
  out on every system.

**Failed starts:** if nobody listens on the pipe in pipe mode, or another server
listens on the name in pipe-server mode, the server logs
`Server failed to start: <reason>`, with a reason that names the pipe, and
exits with exit code 1.

**The socket file:** in pipe-server mode on Linux and macOS, the server replaces
a socket file on which nobody listens, as a server that was killed leaves it
behind. When it stops, it removes its socket file.

## Robot Framework on the server

The server runs Robot Framework itself: it imports the libraries in an
execution of its own and runs their keywords there. A remote keyword therefore
sees the variables of the server's execution, set with `--variable`,
`--variablefile` and `--outputdir`, not those of the suite that calls it; for
example, `${TEST NAME}` is the name of the server's internal test. The values
of its arguments come finished from the client: the server resolves no variables
or escapes in them. Robot Framework converts them by the signature of the
keyword, as for a local library, also by the type of a default: the string
`[3, 4]` becomes a list for an argument whose default is a list. `BuiltIn`
keywords that a library calls, for example to set a variable or to run another
keyword, act on the server's execution, too.

## Starting

The server logs to stderr, whatever the log level of its clients. Once it
accepts clients, it logs
`Server is up and running. Press Ctrl+C to stop.` If the server cannot start, for example because
the port or the name of its pipe is already in use, it logs `Server failed to start: <reason>` and
exits with exit code 1.

In stdio mode, the server needs a stdin that it can watch for input, such as a
pipe. With the null device or a regular file on stdin, and on Windows with
anything but a pipe, it fails to start in the same way. On Windows, it works
with the pipes of any parent: with the overlapped pipes that the client creates,
and with the ordinary pipes of other programs, such as those of `subprocess`.

## Errors and tracebacks

If something unexpected goes wrong while the server handles a request, such as
a call with an unknown library token or a library that fails to import, the
server logs the error with its traceback at `ERROR` level and answers with the
message of the error. A keyword that fails is a test result and is not logged
as an error, and neither is a request that the server refuses, such as the
import of a library that it does not serve. The
[protocol page](/robotframework-jsonrpcremote/reference/protocol/#errors) lists
the error codes.

For debugging from the client's side, start the server with `--send-tracebacks`:
the response to an unexpected error then also holds the traceback, and the
client [shows it](/robotframework-jsonrpcremote/guides/failures/#errors-that-are-not-failures-of-a-keyword).
The option shows the server's code and paths to every client, so keep it for a
debugging session.

## Stopping the server

Stop the server with SIGTERM or SIGINT (Ctrl+C), for example when a container
is stopped. It then:

1. lets the keyword that is running finish and delivers its result to the
   client;
2. answers requests that need Robot Framework (importing or finalizing a
   library, running a keyword) and are still waiting or arrive meanwhile with
   the error `server is shutting down`, code `-32002`, without running them;
3. stops accepting connections, closes every client connection and exits with
   exit code 0.

The server waits up to 5 seconds for the responses that are still being sent
before it closes the connections. A keyword that does not return delays the
stop, since Robot Framework runs it and the server cannot interrupt it. Such a
server has to be killed, as Kubernetes does at the end of a pod's termination
grace period.

The client reports the closed connection as a lost connection for the rest of
its session; see
[Lost connections and connect retry](/robotframework-jsonrpcremote/guides/lost-connections/).
In stdio mode, the server also stops when the client closes the server's stdin,
and in pipe mode when its connection ends.
