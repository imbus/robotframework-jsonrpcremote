`JsonRpcRemote` and the server talk [JSON-RPC 2.0](https://www.jsonrpc.org/specification).
The protocol is language-agnostic by design: a server can be written in any
language that reads and writes JSON over a stream, and JSON-RPC libraries that
support the framing of the Language Server Protocol handle the transport part.

This page describes the messages, for implementing a server of your own. The
package `robotframework-jsonrpcremote-protocol` defines them in the module
`robot_jsonrpcremote_protocol`: the params and results as Python dataclasses,
and both sides as the classes `ServerEndpoint` and `ClientEndpoint`, with the
name and the types of each message in use. The client, the server and the
[example server](#example-a-hand-written-server) at the end of this page use
them.

## Framing

The protocol needs a stream that delivers bytes in order, such as a TCP
connection or the stdin and stdout of a process. Each message starts with a
header part, as in the
[Language Server Protocol](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.18/specification/#headerPart):

```text
Content-Length: 60\r\n
\r\n
{"jsonrpc":"2.0","method":"robot/initialized","params":{}}\r\n
```

- The headers are ASCII, each ends with `\r\n`, and an empty line ends the
  header part. The reference implementation matches header names without regard
  to case, and the space after the colon is optional.
- `Content-Length` is the length of the content in bytes, and it is required.
  The reference implementation ends the content with `\r\n` and counts it.
- `Content-Type` may give a `charset` for the content; the default is UTF-8.
  Other headers are ignored.

A message that the reference implementation cannot read does not end the
connection. It logs the problem and goes on with the next message:

- A header part without a valid `Content-Length` gets no answer, because the end
  of its content is unknown. The bytes that follow are read as the next header
  part.
- A message with an unknown `charset`, or whose content is not valid in its
  charset or as JSON, gets the error `-32700` with `id: null`.

The content can also be a batch, an array of messages as in JSON-RPC 2.0. The
reference implementation handles each element on its own and answers with one
array of the responses. If no element needs a response, it sends nothing.

## Values

- Field names are the names of the dataclass fields, such as `library_token`.
  The reference implementation leaves out optional fields that are not set.
- Arguments and return values of keywords and the arguments of
  `robot/import_library` are JSON values, whose lists and objects may be nested
  to any depth.
- Values are final: a client sends them as they are meant to arrive. The
  reference server resolves no variables or escapes in them. Robot Framework
  still converts them by the signature of the keyword, as for a local library.
- The Python implementation sends a list, and a dict with string keys, whose
  items are all JSON values, as plain JSON, nested to any depth.
- Values of the following kinds travel as typed JSON, in the form of their
  kind:

  | Kind | Form |
  | ---- | ---- |
  | dataclass | an object with its fields |
  | named tuple | an array of its items, by position |
  | member of an enum | its name, such as `"RED"` |
  | `tuple`, `set`, `frozenset` | an array of the items |
  | `dict` with keys other than strings | an array of `[key, value]` pairs |
  | `OrderedDict` | an object, or an array of pairs where its keys are not strings |
  | `float` `NaN`, `Infinity`, `-Infinity` | `"NaN"`, `"Infinity"`, `"-Infinity"` |
  | `datetime`, `date`, `time` | an ISO 8601 string, with the offset where the value has a time zone, such as `"2025-12-18T14:30:00+00:00"` |
  | `timedelta` | its seconds, as a number, such as `90.5` |
  | `Decimal`, `UUID` | a string, such as `"123.45"` |
  | `bytes`, `bytearray` | a Base64 string |
  | `Path` | a string with `/` as the separator |

- Where the signature of the keyword declares the type of an argument or of the
  return value, in the library definition, the value travels in its form, also
  when both sides read pickles, and the receiver builds it by the declared
  type. A value that is not of its declared type travels as if no type were
  declared, and `null` is always `None`.
- Where the signature declares no type, as with `Any`, without a type hint or
  with a union of several types other than `None`, and no pickles are agreed,
  the value names its type in the key `__type__`. A dataclass carries its fields
  next to that key, as in `{"__type__": "mytypes.Point", "x": 1, "y": 2}`; every
  other value carries its form in the key `value`, as in
  `{"__type__": "tuple", "value": [1, 2]}`. Typed values may sit inside lists and
  objects.
- A type is named as in the library definition: a class by its module and its
  qualified name, such as `mytypes.Point`, and the other types by the names that
  Robot Framework gives them, such as `tuple`, `datetime` or `Decimal`. Client
  and server have the same classes installed, in the same modules; a server in
  another language names the Python class and writes its form. The receiver
  imports the class and builds only the kinds above.
- Between Python peers, the Python implementation sends a value that JSON
  cannot hold, at a place that declares no type, as `{"__pickled__": "<hex>"}`,
  where `<hex>` is a Python pickle of the whole value in hexadecimal, so that it
  arrives unchanged. It does so only if both sides read pickles, as they state
  with `pickle_protocol` in `robot/initialize`, and with the lower of the two
  protocols. A side that states no `pickle_protocol` reads no pickles: it gets
  none, and it refuses one that arrives. A server in another language states
  none.
- An object with the key `__pickled__` or `__type__` is never plain JSON: the
  Python implementation pickles a dict with one of these keys, or refuses it if
  no pickles are agreed.
- A value that may not travel, because it is neither plain JSON nor typed JSON
  and no pickles are agreed, fails the call with a `TypeError` that names its
  type and why. A typed value that does not fit its type, or whose class cannot
  be imported, fails it with a `ValueError` worded as Robot Framework words a
  failed conversion, such as
  `Argument 'at' got value '{'x': 1}' (dictionary) that cannot be converted to mytypes.Point: missing field 'y'`.
  The reference server answers such an argument with the code `-32602`, before
  the keyword runs. Where Robot Framework converts an argument itself, such as
  an enum from a name in another case, the conversion and its failure are those
  of a local library.
- Reading a pickle can run arbitrary code; see the caution in
  [Transports](/robotframework-jsonrpcremote/guides/transports/#tcp).

## Methods

| Constant                     | Method                   | Type         | Params                  | Result                  |
| ---------------------------- | ------------------------ | ------------ | ----------------------- | ----------------------- |
| `INITIALIZE_REQUEST`         | `robot/initialize`       | request      | `InitializeParams`      | `InitializeResult`      |
| `INITIALIZED_NOTIFICATION`   | `robot/initialized`      | notification | `InitializedParams`     |                         |
| `IMPORT_LIBRARY_REQUEST`     | `robot/import_library`   | request      | `ImportLibraryParams`   | `ImportLibraryResult`   |
| `RUN_KEYWORD_REQUEST`        | `robot/run_keyword`      | request      | `RunKeywordParams`      | `RunKeywordResult`      |
| `SET_LOG_LEVEL_NOTIFICATION` | `robot/set_log_level`    | notification | `SetLogLevelParams`     |                         |
| `LOG_NOTIFICATION`           | `robot/log`              | notification | `LogParams`             |                         |
| `TRACE_NOTIFICATION`         | `robot/trace`            | notification | `LogParams`             |                         |
| `FINALIZE_LIBRARY_REQUEST`   | `robot/finalize_library` | request      | `FinalizeLibraryParams` | `FinalizeLibraryResult` |
| `SHUTDOWN_REQUEST`           | `robot/shutdown`         | request      | `ShutdownParams`        | `ShutdownResult`        |
| `EXIT_NOTIFICATION`          | `robot/exit`             | notification | `ExitParams`            |                         |

The server sends `robot/log`, and the client every other message; the
reference implementation does not use `robot/trace`.

## A session

A [session](/robotframework-jsonrpcremote/guides/sessions/) is one connection,
on which the client imports one library:

1. The client connects and sends `robot/initialize` with its log level. The
   server answers with its capabilities and information about itself.
2. The client sends `robot/initialized`. The reference server refuses
   `robot/import_library` and `robot/run_keyword` before it has received both.
3. The client sends `robot/import_library`. The server imports the library and
   answers with a token for this instance and the library definition, from
   which Robot Framework learns the keywords.
4. For each keyword call, the client sends `robot/run_keyword` with the token;
   if its log level has changed since it last reported it, it sends
   `robot/set_log_level` first. While the keyword runs, the server sends its log
   messages from that level on as `robot/log`, which the client logs under the
   keyword; then it sends the response.
5. When the session ends, the client sends `robot/finalize_library` with the
   token, then `robot/shutdown`, then `robot/exit` if the server announced
   `support_exit`, and closes the connection. If a connection ends without
   `robot/finalize_library`, the reference server finalizes its libraries itself,
   also one whose import was still running.

## Data structures

### Initialization

- **`InitializeParams`**
  - `capabilities`: `ClientCapabilities` (optional): what the client supports.
  - `client_info`: `ClientInfo` (optional): name and version of the client.
  - `initialization_options`: any value (optional): options for the server.
  - `trace`: string (optional): the initial trace setting, such as `"off"`.
  - `log_level`: string (optional): the log level of the client, one of Robot
    Framework's levels `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR` or `NONE`. The
    reference server sends messages from this level on, and from `INFO` on
    without it.
- **`InitializedParams`**: empty.
- **`InitializeResult`**
  - `capabilities`: `ServerCapabilities` (optional): what the server supports.
  - `server_info`: `ServerInfo` (optional): name and version of the server.
- **`ClientInfo`**, **`ServerInfo`**
  - `name`: string.
  - `version`: string.
- **`ClientCapabilities`**
  - `supports_log`: boolean (optional).
  - `supports_trace`: boolean (optional).
  - `pickle_protocol`: integer (optional): the highest pickle protocol that the
    client reads; without it, the client reads no pickles. The client states
    the highest protocol of its Python, unless `rpc_pickles` is false.

  The client sends `supports_log` and `supports_trace` unset, and the reference
  server does not read them.
- **`ServerCapabilities`**
  - `support_exit`: boolean (optional): whether the server handles
    `robot/exit`. The client sends `robot/exit` only if it is `true`.
  - `libraries`: list of strings (optional): the libraries that clients may
    import, as given on the server's command line; empty if clients may import
    any library.
  - `pickle_protocol`: integer (optional): the highest pickle protocol that the
    server reads; without it, the server reads no pickles. The reference server
    states the highest protocol of its Python, unless it was started with
    `--no-pickles`.

### Library import

- **`ImportLibraryParams`**
  - `name`: string: the library to import. An empty string asks for the
    server's default library; the reference server then imports the first
    library of its command line.
  - `args`: list (optional): positional arguments for the library.
  - `kw_args`: object (optional): named arguments for the library. The
    reference server passes them to Robot Framework as `name=value`, which
    converts them according to the library's `__init__`.
- **`ImportLibraryResult`**
  - `token`: string: identifies the imported library instance in later
    requests. The server chooses it; it is unique for each import.
  - `definition`: `LibraryDefinition`.
- **`FinalizeLibraryParams`**
  - `token`: string: the instance to release.
- **`FinalizeLibraryResult`**: empty.

### Library definition

- **`LibraryDefinition`**
  - `name`: string: the name of the library, as Robot Framework names it without
    an alias, such as `MyLibrary` for `path/to/MyLibrary.py`.
  - `keywords`: list of `KeywordDefinition`.
  - `doc`: string (optional): the library documentation.
  - `doc_format`: string (optional): `ROBOT`, `REST`, `HTML` or `TEXT`.
  - `scope`: string (optional): `GLOBAL`, `SUITE` or `TEST`.
  - `version`: string (optional).
  - `source`: string (optional): the path of the library's source file.
  - `lineno`: integer (optional): the line where the library is defined.
- **`KeywordDefinition`**
  - `name`: string.
  - `args`: list of `ArgumentDefinition`.
  - `doc`: string (optional).
  - `tags`: list of strings (optional).
  - `source`: string (optional): the path of the file that defines the keyword.
  - `lineno`: integer (optional): the line where the keyword is defined. The
    client passes it to Robot Framework with `source`, and ignores it without one.
  - `return_type`: string (optional): the declared return type, written as the
    `type` of an `ArgumentDefinition`; none if the keyword declares none. The
    client builds a typed return value by it.
- **`ArgumentDefinition`**
  - `name`: string.
  - `type`: string (optional): the type hint as text, such as `"int"` or
    `"list[mytypes.Point] | None"`: classes by their module and qualified name,
    the other types by the names that Robot Framework gives them. The client
    passes Robot Framework the classes that it can import, so that Robot
    Framework converts the argument on the client and Libdoc describes the
    class, and the text otherwise.
  - `has_default`: boolean (optional): whether the argument has a default.
    If `true`, `default` holds it, which may be `null`.
  - `default`: any value (optional). The reference server sends a default that
    is `null`, a string, a number or a boolean as it is, and every other default
    as the text that Libdoc shows for it, such as `LEFT` for a member of an
    `Enum` or `[1, 2]` for a list.
  - `required`: boolean: reserved, always `true`. Use `has_default` instead.
  - `kind`: `ArgumentKind` (optional), a string: `POSITIONAL_ONLY`,
    `POSITIONAL_OR_NAMED`, `POSITIONAL_ONLY_MARKER` (the `/`),
    `NAMED_ONLY_MARKER` (the `*`), `VAR_POSITIONAL` (`*args`), `NAMED_ONLY` or
    `VAR_NAMED` (`**kwargs`).
  - `doc`: string (optional).

### Keyword calls

- **`RunKeywordParams`**
  - `library_token`: string: the token from `ImportLibraryResult`.
  - `name`: string: the keyword name from the library definition. A keyword with
    embedded arguments goes by that name too, such as `Add ${count} Items`, and
    `args` starts with their values.
  - `args`: list (optional): positional arguments.
  - `kwargs`: object (optional): named arguments.
- **`RunKeywordResult`**
  - `result`: any value (optional): the return value of the keyword.
  - `error`: `RunKeywordError` (optional): set if the keyword failed.
- **`RunKeywordError`**
  - `message`: string: the client fails the keyword with exactly this message.
    The reference server sends the message that Robot Framework shows for the
    same error of a local keyword, such as `ValueError: bad value`. A server
    sends the whole message, however long: what the report shows is up to the
    Robot Framework run of the client.
  - `type`: string (optional): the name of the exception, such as `"ValueError"`.
    The client does not read it.
  - `traceback`: string (optional): the client logs it at the level `DEBUG`
    under the keyword, with `[remote] ` in front.
  - `mode`: `RunKeywordErrorMode` (optional), a string. Without it, the failure
    is a normal one.
    - `SKIP`: the client skips the test with the message.
    - `CONTINUABLE`: the test continues and fails at its end.
    - `FATAL`: the client stops the run. The reference server keeps running.

  The reference server sets all fields, the `mode` if there is one. It reports
  only a keyword that ran and failed this way; see [Errors](#errors).
  [Failures of remote keywords](/robotframework-jsonrpcremote/guides/failures/)
  shows how the failures appear in Robot Framework.

### Log messages

- **`LogParams`**
  - `message`: string.
  - `level`: `LogLevel` (optional), a string: `TRACE`, `DEBUG`, `INFO`,
    `WARN`, `ERROR`, `CONSOLE` or `HTML`. Without it, the client logs at `INFO`.
    At `TRACE` and `DEBUG`, it puts `[remote] ` in front of the message, to tell
    it from its own messages at these levels.
  - `html`: boolean (optional): whether the message is HTML.
  - `console`: boolean (optional): whether the client also writes the message
    to the console. Without it, the client does as Robot Framework does for a
    local library: `WARN` and `ERROR` go to the console, other levels do not.
    With `false`, a warning stays off the console from Robot Framework 7.4 on.
  - `timestamp`: string (optional): when the message was logged. The client
    does not read it.
- **`SetLogLevelParams`**
  - `log_level`: string: the new log level of the client, as in
    `InitializeParams`.

  A server may send all its messages and ignore the log level: the client logs
  only the messages from its log level on.

### End of a session

- **`ShutdownParams`**, **`ShutdownResult`**: empty. The client announces that
  it is about to close the connection.
- **`ExitParams`**: empty. Sent with `robot/exit`; the server then closes the
  connection.

## Errors

A keyword that ran and failed is not a JSON-RPC error: the response is a
`RunKeywordResult` with `error`, also for a wrong number of arguments, which
Robot Framework reports as a failure of the keyword.

Every other request that the server cannot complete gets a JSON-RPC error
response. The client fails the library import or the keyword call with its
`message`. It logs `data`, if there is any, at the level `DEBUG` under the
keyword, with `[remote] ` in front; at a library import, `data` follows the
message. The reference server answers with these codes:

| Code     | Name in the protocol                      | Answers |
| -------- | ----------------------------------------- | ------- |
| `-32000` | `RobotJsonRpcErrorCode.NOT_INITIALIZED`   | A library import or a keyword call before the handshake is complete. |
| `-32001` | `RobotJsonRpcErrorCode.KEYWORD_NOT_FOUND` | A keyword that the library does not have. |
| `-32602` | `INVALID_PARAMS` of JSON-RPC              | The import of a library that the server does not serve, an import without a name if the server has no default library, and params that cannot be converted. |
| `-32601` | `METHOD_NOT_FOUND` of JSON-RPC            | A method that the server does not have. |
| `-32600` | `INVALID_REQUEST` of JSON-RPC             | A message that is not a JSON object, an empty batch, a message whose `jsonrpc` is not `2.0`, and a message without a `method` as a string, with `params` that are neither an array nor an object, or with an `id` that is neither a string nor an integer. It carries the `id` of the message if that is a string or an integer, and `null` otherwise. |
| `-32700` | `PARSE_ERROR` of JSON-RPC                 | A message that is not valid JSON, with an unknown `charset`, or whose content is not valid in its charset. |
| `-32603` | `INTERNAL_ERROR` of JSON-RPC              | Anything else, such as an unknown library token, a return value that cannot be transferred, a library that fails to import, or a server that is stopping. |

The error of a library that fails to import has the message of Robot Framework,
with the traceback of the library's code and the module search path.

A notification and a response are never answered, not even when they are
invalid. The reference implementation logs what is wrong with them. An invalid
response with the `id` of a waiting request fails that request.

An error response carries no traceback, unless the server was started with
`--send-tracebacks`; see
[Server options](/robotframework-jsonrpcremote/reference/server/#errors-and-tracebacks).
A server in another language may set `data` to anything that helps to find the
cause.

### Over a pipe

For a `pipe:` URI, the client listens on a new pipe and starts the command with
`--pipe=<address>` as its last argument, as editors start language servers. A
server that the client starts this way connects to that address, serves the one
client there and exits when the connection ends. The address is:

- on Windows, a named pipe, such as `\\.\pipe\jsonrpcpeer-<32 hex digits>`;
- elsewhere, the path of a Unix domain socket in a new directory that only the
  user can enter, such as `/tmp/jsonrpcpeer-k2v9x1qa/pipe`.

The client takes the first connection to the address and then stops listening.
The server's stdin is the null device, and its stdout and stderr go to the
stderr of `robot`, so the server can print as it likes: the messages have a
connection of their own.

With `--pipe ADDRESS`, also written `--pipe=ADDRESS`, the example server
connects with `open_pipe_connection()` from `jsonrpcpeer`, so that the client
can start it with a `pipe:` URI, as
[Transports](/robotframework-jsonrpcremote/guides/transports/#a-server-that-the-client-starts)
describes:

<Code code={pipeSuite} lang="text" title="echo_pipe.robot" />

In another language, the functions of the platform for these connections are
enough; in Node, for example, `net.connect(address)` connects to both kinds. A
server that suites connect to with `pipe://<name>` listens on the pipe instead,
as `robot-jsonrpcremote-server --pipe-server <name>` does; see
[Transports](/robotframework-jsonrpcremote/guides/transports/#a-server-that-listens-on-a-pipe).

On Windows, a pipe opened for synchronous I/O, as `open()` in Python opens it,
handles one operation at a time: a write waits until a pending read has
returned. A server that reads a request and then writes its response can use
it. One that reads and writes at the same time, such as one with a thread that
waits for the next message while another sends log messages, has to open the
pipe for overlapped I/O, as `open_pipe_connection()` and Node's `net` do.

### Over stdin and stdout

With `--stdio`, the example server serves one client over its stdin and
stdout, so that the client can start it with a `stdio:` URI, as
[Transports](/robotframework-jsonrpcremote/guides/transports/#stdio)
describes:

<Code code={stdioSuite} lang="text" title="echo_stdio.robot" />

For this, the example calls `open_stdio_connection()` from `jsonrpcpeer`. It
returns a reader and a writer for the stdin and stdout of the process, for a
`JsonRpcPeer`, and moves the standard streams out of the way of the messages:
what the process or one of its child processes writes to stdout goes to
stderr, and reading stdin gives the end of the input. So the output of the
example's `print()` calls appears on its stderr, and so on the console of
`robot`.

A server that does not use `open_stdio_connection()`, such as one in another
language, must write nothing but messages to its stdout over stdio.

On Windows, the client creates the stdin and stdout of the server as
overlapped pipes, so that a Python server can use I/O completion ports.
Programs in other languages read and write them as usual, with one reader and
one writer. Do not let anyone else use these pipes: a child process that
inherits stdin or stdout, or a second handle in another thread, can lose data
or crash the process. Start child processes with their own stdin and stdout.
